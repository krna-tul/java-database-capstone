# Smart Clinic Database Design

## Resources and storage choices

MySQL database `cms` stores administrators, doctors, patients, appointments and doctor availability. These records need stable identifiers, relational joins and foreign-key integrity. MongoDB database `prescriptions`, collection `prescriptions`, stores prescription documents. Optional doctor notes fit the document model; `appointmentId` connects a document to its MySQL appointment.

## MySQL schema

| Table | Columns and constraints |
| --- | --- |
| `admin` | `id BIGINT` identity primary key; `username VARCHAR(255)` required, unique; `password VARCHAR(255)` required and excluded from JSON output |
| `doctor` | `id BIGINT` identity primary key; `name VARCHAR(100)` required, 3–100 characters; `specialty VARCHAR(50)` required, 3–50 characters; required unique `email VARCHAR(255)`; required `password VARCHAR(255)` with minimum 6 characters, excluded from JSON output; required `phone VARCHAR(10)` containing exactly 10 digits |
| `doctor_available_times` | required `doctor_id BIGINT` foreign key to `doctor.id`; required `available_times VARCHAR(255)` such as `09:00-10:00`. Mapped using `@ElementCollection`; rows belong to one doctor |
| `patient` | `id BIGINT` identity primary key; required `name VARCHAR(100)` (3–100 characters), unique valid `email VARCHAR(255)`, `password VARCHAR(255)` (minimum 6 characters, write-only JSON), `phone VARCHAR(10)` (10 digits), `address VARCHAR(255)` |
| `appointment` | `id BIGINT` identity primary key; required `doctor_id` and `patient_id` foreign keys; `appointment_time DATETIME(6)` required; `status INT` restricted to 0 (scheduled) or 1 (completed). Indexes on doctor/time and patient/time support calendar queries |

A doctor has many appointments; a patient has many appointments. Each appointment references exactly one doctor and one patient. Foreign keys prevent orphaned appointments. Deleting a doctor or patient with appointments is restricted until dependent records are handled explicitly. Availability is a separate collection table, not a comma-separated string.

The executable DDL is [database/schema.sql](database/schema.sql). JPA models can also generate the five tables using Hibernate. Application validation additionally checks email format, string lengths, phone format and a future appointment time. The primitive `int` status uses `@Min(0)`/`@Max(1)` because `@NotNull` cannot validate a primitive. Historical fixtures are inserted directly by SQL for reporting exercises; their dates deliberately remain in 2025.

## MongoDB document schema

Database: `prescriptions`. Collection: `prescriptions`.

```json
{
  "_id": "demo-rx-01",
  "patientName": "John Smith",
  "appointmentId": 51,
  "medication": "Demo medication",
  "dosage": "Demo dosage",
  "doctorNotes": "Fictional training record.",
  "_class": "com.project.back_end.models.Prescription"
}
```

`_id` maps to a Java String and may be generated by MongoDB when omitted. `patientName` and `medication` are required, 3–100 characters. `appointmentId` is a required positive Long. `dosage` is required, 3–20 characters. `doctorNotes` is optional and limited to 200 characters. `_class` is Spring Data type metadata. The course model has one medication and dosage per document, so a flat document is sufficient; no artificial nested structure is needed. If multiple medications are introduced later, an embedded `medications` array containing `{name, dosage}` objects would be a schema extension requiring a corresponding Java model change.

MongoDB cannot enforce a foreign key into MySQL. The service layer must verify `appointmentId`, check permissions and coordinate cleanup; a snapshot of the patient name is useful for display but the appointment is the authoritative link. No cross-database transaction is claimed here.
